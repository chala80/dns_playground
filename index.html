Split DNS

  • BIND has two views. Resolvers in 10.0.0.0/8 get the internal view, everyone else external. Both CNAME the apps into gtm.chala.info, but the delegation points to the listeners' internal or public (NATed) addresses.
  • On BIG-IP DNS each wide IP has two pools. The wide IP uses Topology: an LDNS in region internal_nets scores pool _int (10.x answers), any other LDNS scores pool _ext (public answers).
  • External virtual server objects use a translation address, so gtmd answers the public address while big3d still monitors the private one.

Delegating to BIG-IP DNS

  • BIND stays authoritative for chala.info. Each app name is a CNAME: app1.chala.info → app1.gtm.chala.info.
  • gtm.chala.info is delegated with NS records to the BIG-IP DNS listeners, so a resolver following the CNAME asks gtmd, which answers from the wide IP.
  • The resolver caches each piece for its own TTL: BIND's CNAME and NS for hours, gtmd's A record for the pool TTL (30 s by default), so GSLB decisions are picked up quickly.

GSLB on BIG-IP DNS

  • A wide IP (app1.gtm.chala.info) points to a GTM pool. Its members are virtual servers on server objects: BIG-IP LTMs or generic hosts.
  • gtmd picks an available member with the pool's load balancing mode. Round Robin alternates. Global Availability uses the first available member in order. Round Trip Times picks the data center closest to the LDNS, using the alternate mode until path metrics exist.
  • If no member is available, the fallback mode applies (return-to-dns here).

Monitors, probers and generic hosts

  • bigip sends no probe. The LTM's big3d reports the status of its own virtual servers to every connected gtmd.
  • Custom monitors (http, https, tcp, gateway_icmp) need a prober: a big3d chosen by the server's prober preference, then its fallback. It probes the member and sends the result to every connected gtmd.
  • A generic host runs no big3d, so it has no iQuery connection and can't use bigip. Everything gtmd knows about it comes from probes sent by BIG-IP big3d agents.

iQuery and big3d

  • iQuery is XML over TCP port 4353, wrapped in TLS. Trust comes from device certificates exchanged with bigip_add or big3d_install.
  • gtmd on every DNS device connects to big3d on every BIG-IP server it knows, itself included: 8 connections here.
  • A gtmd that loses its connection to a big3d stops hearing that big3d's results, so two DNS devices can disagree.

About this model

1× is real time and uses BIG-IP defaults: iQuery heartbeat 10 s, bigip monitor 30 s / 90 s, custom monitors 30 s / 120 s, path TTL 2400 s, pool TTL 30 s. Use 5× to 20× to skip ahead. Packets in flight are slowed down so you can see them; real iQuery and DNS messages take milliseconds. The LDNS is assumed to already know where chala.info lives, so root and .info lookups are skipped. Internal and external virtual server objects share one status per real server here; on a real system each is monitored separately. Log lines, iQuery XML and the config tabs are modeled on real output but simplified, so check a real device for exact text. Real CLI to try: tmsh show gtm iquery, tmsh show gtm pool a, dig app1.chala.info +trace, iqdump 10.1.10.10.
